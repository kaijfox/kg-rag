# A map of a codebase

The map is made of what the code's own documentation says. Your agent writes a short comment on each class and function that
says what it is for and how it works inside. Your language's documentation generator (TypeDoc, pdoc, Sphinx, rustdoc and
similar) turns the comments into a folder of pages, and kg-rag reads those pages as they are.

Comments sit next to the code they describe, so an agent that changes a function sees the comment it must keep true. The
pages are generated by a program, not written by a model, so they cannot add claims the comments do not make.

kg-rag does not run the generator, convert its output or know where in the source a symbol lives. A result tells the agent
which page and heading it came from, and the agent finds the code by that symbol name.

## Prompt for your agent

```markdown
## Code documentation

Before you commit, update the documentation comments of every class, method and function whose body you changed, and add
them where missing. Do not rewrite comments of code you did not change. These comments are developer documentation: they
are read by someone deciding what to change or where a behaviour comes from.

For each one write:
- Purpose: why it exists, in one sentence that does not repeat its name.
- Contract: what it takes and returns, what it throws, and what it changes outside itself (files, network, logs).
- How it works: the main steps in order, the conditions it relies on, and any choice that is not obvious, with the reason.
- What not to change without also changing something else, when the body shows it.

Rules:
- Everything you write must be checkable from the function's own body. Do not list its callers, and do not describe other
  files. That goes out of date without anyone noticing.
- Name things in full. Do not write "it" or "this" for something defined elsewhere.
- Keep each comment under about ten lines. A longer one means the function does too much.
```

## Build and read the pages

Run your generator so that it writes HTML into a folder outside your repository (so the folder is not read twice), then add
that folder as a source:

```sh
npx typedoc --out ~/kg/myproject-docs/site --entryPoints src --entryPointStrategy expand \
  --excludePrivate false --skipErrorChecking
/path/to/kg-rag/kg add ~/kg/myproject-docs/site --adapter html --exclude '(^|/)(assets|hierarchy|modules)(\.html|/)|^index\.html$' --db ~/kg/myproject
/path/to/kg-rag/kg ingest --db ~/kg/myproject
```

The TypeDoc options matter. Developer documentation is mostly about internal code, and TypeDoc leaves out private members
unless told otherwise. For Python, `pdoc -o ~/kg/myproject-docs/site mypackage` and `sphinx-build -b html docs
~/kg/myproject-docs/site` write the same kind of folder, and the `kg add` line is the same except for `--exclude`.

The `html` adapter is general: it does not know which tool wrote a page. Headings become the section path, the text under
each heading becomes passages, and navigation, scripts and sidebars are skipped. `--exclude` is a regular expression matched
against each file's path inside the folder; use it to leave out pages that only list or index other pages. A passage whose
text did not change keeps its identity, so after a commit only the symbols whose comments changed are embedded again.

## What each generator gives you

These are the limits we saw on real pages from each tool.

- **TypeDoc** writes a heading per member, so each member becomes its own passage. This is the best case. Its pages also carry
  an "On This Page" menu and "Preparing search index..." text, which add a little noise to results. TypeDoc leaves out the
  comment at the top of a file unless it contains a `@module` tag, and many projects put their explanation of how a file works
  there. Add `@module` on its own line at the end of that comment, or put the explanation on the functions.
- **Sphinx** writes little structure per symbol, so passages are coarser: several functions often share one passage.
- **pdoc** embeds each module's whole source in "View Source" blocks, and these become passages. On the Python sidecar in this
  repository they raised the index from 11 to 57 passages and the text returned per search from about 3,000 to about 4,600
  characters, with no gain in finding the right module. Pass `--no-show-source`.

Source code itself is not indexed and no file or line is stored. If you want the agent to search code text, that is a
different job from this one and is not covered here.

## Rebuild on commit

Copy `post-commit.sh` from this folder to `.git/hooks/post-commit`, set the three paths at its top, and make it executable.
It runs the documentation build and `kg ingest` after each commit. Do not also start `serve mcp --watch` on the generated
folder; use one or the other.

## What we measured

On kg-rag itself (50 source files), twenty questions about the code each had the file that answers them. Searching the
TypeDoc pages found a page about that file in the top five results for 15 of 20 questions (13 at the first result). Four of
the five misses returned pages from related files instead, and the fifth was a near-miss on a similarly named file. The
script is `experiments/code-map-selftest.mts`. The questions were written by the author of the code and the comments in that
repository are uneven, so treat this as a check that the route works, not a measure of how good a map is. Your searches will
tell us more.
