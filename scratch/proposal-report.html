Proposal · 6 November 2026

A leaner engine for retrieval over knowledge graphs

Coding and research agents need background knowledge that no single passage supplies. A first build produced a sound way to measure retrieval and no improvement in retrieval. This report assesses that build against a small reference system, nano-graphrag, and proposes a smaller engine made of interchangeable parts.

Finding. The foundation (content-derived chunks with source links) and the measurement rig worked. The richer record types (facts, summaries, links) are designed but unbuilt. The packaging around all of it did not work: 17 software packages, a workflow engine wrapped around every pipeline, and a PDF-processing effort that is not the project's subject.

Comparison. nano-graphrag was cloned and read. Its data model suits whole-corpus synthesis and has no place for qualified facts, undoable merges or revision. The first build’s design has the reverse profile, and most of it is unbuilt.

Proposal. Start from GraphRAG’s shape (chunks, extracted facts, a graph, optional summaries, query modes) instead of the first build’s model. Section 10 ties each design choice to a finding. A fact is a standalone sentence that cites its chunks. An index is rebuilt on upgrade and never versioned, and the log, evaluation results and confirmed corrections live in a separate durable store. Each way of answering is a state machine over small modules. The cost table in section 9 takes the first design’s 25 tables to 17 and postpones the most expensive demands until a measurement asks for them.

Decision requested. Approval to adopt this design (a simplified model in GraphRAG’s shape, modules wired by state machines, PDF parsing behind an adapter, and the staged build order) before choosing the first retrieval improvement (section 11).

1. The need

Agents that write code or research need background knowledge from two sources: papers and textbook chapters on one sub-domain, and the working history of a project. The questions they ask are often answered by no single passage. Two examples show the pattern.

  • Combining facts. “Which method handles case X?” may need a fact from one paper and a condition from another.
  • Change over time. A project note from 1 October says the store is JSON files. A note from 17 October says it is SQLite, replacing the JSON files. A correct answer to “what is the store?” is SQLite, and a system must know that the second note supersedes the first. This example recurs below.

The system must also be improvable. Retrieval will fail in places that cannot be predicted. Each failure therefore has to be traced to a stage (extraction, merging, retrieval, answering) so that one stage can change without rebuilding the rest.

Published graph-based systems each fit part of this. GraphRAG extracts entities and relationships from text, groups them into communities and pre-writes a summary of each, which suits whole-corpus questions. LightRAG and nano-graphrag are lighter versions. HippoRAG ranks passages by walking a graph, which suits multi-hop questions. All four report only end-to-end answer quality, so a failure cannot be attributed to a stage. None, by their published descriptions, tracks which fact is current after a revision. Their ideas (fact extraction, graph walks) transfer. Their fixed pipelines do not.

2. Terms used in this report

Chunk
A passage of source text. Its ID is computed from its content, so unchanged text keeps its ID when a document is loaded again.
Derived item
Anything produced from chunks by a model or a program. A fact is a standalone sentence that cites its chunks and lists the names it mentions. A summary cites many chunks. Each derived item lists the chunks it came from.
Module
A function with a name, a version, and a declaration of which intermediate results of one request it needs and which it adds (for example “candidate chunks”). A module does one job: embed a query, find nearest chunks, cut a list to k.
State machine
A fixed set of states and allowed moves between them. Here each state calls one module, and the machine chooses the next state. A loop is a move back to an earlier state.
Kernel
The fixed foundation under every state machine: the data store, the runner that executes machines and records which module versions ran, and the log of every step. Evaluation and viewing tools are clients of it and are not part of it.
Index
The data derived from source documents: chunks, derived items, links and embeddings. An index can be rebuilt from the source files.
History
The durable record of use: event log, agent feedback, evaluation results and corrections that a person confirmed. A rebuild leaves it untouched.
Snapshot
In the first build only, a fixed record of which chunks and derived items are current at a moment, so that two versions of the index can be compared on identical questions.

3. What the first build produced

The first build (four work periods, called sprints in the project files) deliberately added no knowledge graph, so that a baseline and a measurement existed before any layer, and each layer could be compared against them. It built plain similarity search over chunks, wrapped in four supports:

  • content-derived chunk IDs and snapshots, so results stay comparable across re-loads;
  • a log of every search step, recording which candidates were considered and how they ranked;
  • a rule, audited in the database, that every derived item cites its source chunks;
  • an evaluation harness. A local language model writes questions with known supporting passages; a second pass scores recall (were the supporting passages retrieved) and answer quality on a 0 to 1 scale judged by a model. On a 30-answer sample the judge agreed with a stronger model at kappa 0.74 (1 is perfect agreement, 0 is chance).

The test corpus was two statistical-mechanics textbooks by different authors. 113 drafted questions were reviewed by a model against a fixed rubric, leaving 63. Of these, 40 were single-hop (one passage suffices), 12 multi-hop (several passages are needed) and 11 topic-level (a whole section is needed).

Results

  • The baseline is strong. For single-hop questions the right passage ranks first in 31 of 40 cases and within the top 20 in all of them.
  • The test is too easy to rank improvements. Answers written with no retrieved context already score 0.73 to 0.80. Perfect context adds only about 0.2. A layer that helps by less than that cannot show.
  • Topic-level questions are the one visible weakness. The sample is 11 questions, so the figure is indicative.
  • Multi-hop retrieval is untested. The 12 multi-hop questions that survived review are easy, and no hard one survived.
  • A fact-extraction trial was promising but unfinished. On 24 passages, the needed fact appeared as an extracted fact in 20 (83%). Of 40 sampled facts, 24 (60%) read as clean sentences that make sense alone, without references such as “the chapter” or “Equation 2.100”.
  • A cheap candidate exists. For 14 of 63 questions the supporting passages are adjacent in the source, so pulling in neighbouring chunks needs no extraction.

The open problem is that the rig is expensive to extend.

4. What went wrong

Three whole-codebase reviews at the end of the build, each covering a different slice, found the same thing: the code around the data model is over-built.

Two things worked and are the reason the project is worth keeping. A database audit of source links found zero violations across the 312 chunks of the first run on the real textbooks. For derived items the audit passed vacuously, because none had been written. And the step-level log let reviewers see why individual queries failed, which none of the four published systems offers.

5. The two data models

nano-graphrag is a minimal reimplementation of GraphRAG, written to be modified. The project cloned it and read its storage code. This section covers only what each system stores. Section 6 covers what each does with it. The first build’s model is shown as designed in the original design document. Its tables exist in the database, but no code writes to most of them, and the diagram marks which.

Strengths and weaknesses of the structures

nano-graphrag. The entity record is a ready anchor: a name, a merged description and a vector in one place. The community record, with its level and member lists, is a ready unit for whole-corpus summaries. Six record types make the whole model easy to hold in mind. The weaknesses are structural. A fact has room for two entities and one description, so conditions and qualifiers must be written into the text. Provenance is a string, so no record says which chunks support a fact without parsing it. Nothing records how two entities came to share a record. Nothing records a version. An entity has one type label from a list written for news text. A community report refers to entities and says nothing about concepts.

First build. The strengths are a separate, content-free node, so a name stays a handle and nothing else; a fact joined to any number of nodes that keeps the name as written; equivalence held in its own records, which never touch the records they join; queryable provenance; snapshots; and embeddings apart from content. The weaknesses are these. A node with no content cannot anchor retrieval the way an entity does, and the model holds no place for an entity’s attributes. A summary has a flat member list and no level or cluster structure. The model has twelve record types, and five are empty. None of it has been tested against the questions it was designed for.

7. How each model supports the extensions in the original design

The original design planned layers above plain similarity search: extracted facts and a graph, graph walks, merging of duplicates, summaries of communities, reranking and query decomposition, and, for project histories, supersession. Each cell separates what the model stores from what an operation does with it.

Where extracted relationships fit

Extracted relationships were central to the original design, and the first build stopped short of them. In the first build’s design an extractor reads one chunk and returns a self-contained fact together with the names it mentions. The fact is both what is embedded and what an agent reads, so it states its own qualifiers (“In rats, lesions of dorsolateral striatum kept responding sensitive to devaluation after extended training”). The design assigns it an ID from the extractor’s version, its source chunks and its text, and refuses it if it cites no chunk. The text enters the ID because models give different facts from the same input, and a new fact should become a new record. The graph is the set of facts joined through shared names. A graph walk then reads three things from a read-only view: the facts that mention a name, the names a fact mentions, and the facts citing a chunk.

In nano-graphrag the same sentence becomes entities and a pair edge, and the qualifiers survive only if the description carries them. Its merged descriptions then mix facts from many chunks.

The open work is the extractor itself (40% of sampled facts were not clean standalone sentences), the node-embedding scheme, and the stored-fact interface.

Verdict

The two models are strong in different places. nano-graphrag fits synthesis: entities as anchors, communities and reports as retrieval units. The first build’s design fits precision, change and diagnosis: qualified facts, links instead of overwrites, and traceable steps. Neither supports concept frameworks, and the first build’s refinement links are only a candidate. The first build was also not set up to test synthesis questions, since its 11 topic-level questions and the absence of summaries as derived items give almost no evidence either way. The proposal in section 10 takes nano-graphrag’s shape as the starting point and adds the first build’s strengths only where the project needs them. Community detection and report writing become whole-collection modules, and nano-graphrag’s three query modes become machines.

8. Assessment of the two hypotheses

The core model was clunky: partly. The record model passed its audits where it was built, and most of it is not yet built. What is clunky is the wrapping: a package, a versioned interface agreement and a state machine for each step, including steps nobody swaps.

The scope was too broad: yes. The system took on PDF-to-text conversion, formula recognition, machine diagrams and a second, throwaway implementation of the whole system kept only for cross-checking. Docling, an existing PDF parser, already does the parsing. The system needs only to accept its output.

nano-graphrag’s modularity is right in kind and misplaced in level. It makes storage and models swappable, which this project has fixed and need not abstract. It leaves the algorithms fixed, and the algorithms are what this project needs to vary.

9. What the project demands, and what each demand costs

Each demand in the original design is weighed on three axes. Concept counts the new ideas a person must hold. Database counts the tables and constraints added. Algorithm counts the code, with extra weight for model dependence and order dependence. The ratings are the author’s judgement from the first build’s records and reviews.

The cheap demands (provenance, content-derived IDs, step logs) carry most of the value. The expensive demands (verified merging, communities, concept frameworks) all need a model to judge many items against one another, and a measurement can postpone each. The first build paid for several of them in its schema before any measurement asked.

10. Proposal: a flexible GraphRAG on a small engine

The data model grows from the baseline one record at a time, and amber marks what each figure adds.

Baseline: documents, chunks, embeddings

Baseline search is strong (the right passage is in the top five for 38 of 40 single-hop questions), so these three records stay. A chunk’s ID is computed from its text, so re-loading unchanged text changes nothing and evaluation questions pinned to chunk IDs stay valid.

Derived items: facts and summaries

Topic-level questions (36% have all supporting passages in the top five) and multi-hop questions need information that no single chunk holds. nano-graphrag derives it as entity descriptions and pairwise edges, which merge text from many chunks and lose qualifiers such as species or conditions. A derived item is instead a fact, one standalone sentence that carries its own qualifiers, or a summary. Each item cites its source chunks, so any answer traces back to text, and facts are embedded and searched like chunks.

Mentions: connecting facts through names

Multi-hop answers join facts that share an entity, while nano-graphrag ties a fact to exactly two entities and keeps one merged description per entity. Here a fact lists any number of names it refers to. Facts that mention the same name are connected, and these connections form the graph. An entity has no record of its own. It is a name plus the facts that mention it, so no merged description needs repair.

Links and version stamps

nano-graphrag overwrites an earlier source when a later one replaces it, and nothing marks which is current. The extraction pilot also found about 10% duplicate names. A link relates two records and edits neither. A “replaces” link marks the newer fact, which current-state queries follow. An “alias of” link says two names mean one thing, and deleting it undoes the merge. A link exists only when the source’s own wording or a checked judgement supports it.

Each derived item and link records the module and version that made it, because a better extractor will arrive and a rebuild must know which records it changes.

Three stores and rebuild

A better extraction prompt changes every fact that the old prompt produced. The first design handled that by keeping old and new results side by side, at the cost of six extra tables for snapshots and checksums. The proposal discards the old index and rebuilds it from the source documents, which costs rebuild time and no versioning machinery. Developers still compare two pipelines by building two indexes and matching records by source chunk. A rebuild would erase three things, so each stays outside the index.

  • The event log, feedback, evaluation results and corrections that a person confirmed live in a durable store, the history, keyed to chunk IDs and names.
  • Model calls take minutes and vary between runs (evaluation runs took 25 minutes to 2 hours), so a cache of model responses makes a rebuild fast and repeatable.
  • A rebuild starts from the original documents and their parsed form, which stay as source files.

The index holds everything else. A rebuild command builds a new index and swaps it in, and gives it an ID that events and evaluation results record, so results from different indexes stay distinguishable.

The cache keys each response by a hash of model, prompt and input, and covers calls that take minutes (extraction, summaries, answering, judging). An extraction response is 2 to 4 KB and a chunk needs one to three calls, so 10,000 chunks fit in under 100 MB compressed. The estimate is unmeasured. The cache is pruned to a size cap, and losing it only slows a rebuild.

Two rules of the original design change form. The stale-build check becomes a query for facts that cite no current chunk, where a chunk is current if it belongs to its document’s latest ingest. Each logged event records the index ID in place of a build.

Engine: modules and state machines

The first build packaged every step with its own interface agreement and state machine, which cost more than the data justified. nano-graphrag errs the other way: algorithms are welded to storage and query modes are chosen by an if-chain. A module is one function that declares which intermediate results of a request it needs and which it adds. A state machine is a short list of module calls with routes between them, checked when it loads. The kernel writes each result, stamps it with the module’s name and version, rejects a fact that cites no chunk, and logs every step.

Each row of the figure needs the records from one step above: chunk search needs the baseline, “facts and neighbours” needs facts and mentions, and “current state” needs links. A whole-corpus mode like GraphRAG’s would add modules that pick summaries and ask a model about each, with no change to the kernel.

nano-graphrag’s extraction prompt with its second pass, its community detection and its report prompts can port as modules, and its storage code does not. Algorithms read the index through a narrow view: facts that mention a name, names in a fact, and facts that cite a chunk. The same evaluation questions can then run through nano-graphrag’s modes and the new machines. PDF parsing and formula decoding took five packages and lie outside the project’s subject, so an adapter turns source files into documents, with docling as one adapter and formula decoding as one of its options.

11. Build order, evidence and decision

Each stage ends with a measurement against the baseline on the 63 pinned questions. Stages 3 and 4 also need the harder question set that the first build lacked.

Evidence. A 138-line module layer exists in the repository. One search step moved onto it and shrank from about 40 lines to 17, with all 92 search tests passing unchanged. The adjacent-chunk signature (14 of 63 questions) and the extraction pilot (83% fact coverage, 60% clean facts) come from the baseline measurements. The simplified data model is neither built nor tested.

Risks. The simplified model may prove too thin, for example if links must record the state they were computed from. Schema migrations make adding a table routine. Extraction quality may block stage 3, in which case stages 2 and 4 proceed. A rebuild needs the source files, and without a warm cache it takes hours on a large corpus with a local model. Intermediate results shared across unlike modules are hard to type. A small fixed vocabulary, extended only when a second module needs an addition, limits that cost.

Decision requested. Approval of five points: the three changes and the simplified data model; a rebuildable index with a durable history and an optional cache; modules wired by state machines under a small kernel; PDF parsing behind an adapter; and the build order. The proposal drops the snapshot manifests that the original design placed in v0, which is a scope change. Stage 1 costs one work period and yields no retrieval gain.
