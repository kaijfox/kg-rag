We want a retrieval system that gives LLM coding and research agents background knowledge, accessed through a tool interface. The knowledge comes from two sources: papers and textbook chapters about one sub-domain (a class of theoretical models, a computational method, a biological system), and the working history of a project (decisions, revisions, what superseded what). In both cases the questions agents ask are often not answered by any single passage. They require combining facts scattered across a corpus, or knowing how an earlier decision relates to a later one. We also need the system to be improvable. We expect it to perform poorly in places we cannot predict, so we need to see where, and change that part without rebuilding the rest.

Microsoft’s GraphRAG has an LLM extract entities and relationships from each text chunk, attaches a written description to each, merges entities that share a name, partitions the resulting graph into hierarchical communities with the Leiden algorithm, and pre-writes a summary report for each community. Its target is “global” questions about a whole corpus (e.g., “what are the main themes?”), answered by combining community summaries. Our questions are mostly specific (what a model assumes, which method handles a given case), and the needed detail sits in a few passages that community summaries abstract away. Name-based merging also fits scientific text poorly, where “dorsolateral striatum” and “striatum” must stay distinct while one structure under two names should merge. The community summaries depend on the whole graph, so a changing corpus forces recomputation of the affected summaries.

LightRAG and nano-graphrag are lighter. LightRAG keeps entity and relationship extraction with descriptions, drops the community hierarchy, and retrieves by matching a query to entities (for specific questions) or to relationship keywords (for broad ones). It also supports adding documents incrementally. nano-graphrag reimplements GraphRAG in a few hundred lines meant to be modified, which makes it the closest in spirit to what we want and a useful reading reference. Two mismatches remain. The retrieval unit is an entity or a pairwise relationship, so a fact involving several entities, or carrying a qualifier such as species or training condition, must be compressed into a description attached to one pair. And incremental addition means appending, not reconciling: to my understanding, when a later document revises an earlier one, descriptions are merged or summarized together and nothing records which is current. That is tolerable for paper-derived knowledge but is the central problem for project histories.

HippoRAG extracts subject–relation–object triples, builds a graph over the extracted phrases, links near-synonyms when embedding similarity exceeds a threshold, and runs personalized PageRank from the nodes matching the query. HippoRAG 2 adds passage nodes and combines the graph with dense retrieval. This is the best match for multi-hop retrieval, and we plan to adopt the PageRank step. The mismatches are the fixed triple form, which discards qualifiers, and the single global similarity threshold, whose correct value will differ across domains. It is also research code evaluated on multi-hop question benchmarks over encyclopedic text, so its behavior on dense technical papers or project logs is unknown. All four systems report end-to-end answer quality, which cannot show whether a failure came from extraction, entity merging, retrieval, or generation, and that attribution is what we need to order our work. The methods are therefore not unworkable for us: the extraction and PageRank ideas transfer, while the fixed pipeline choices, the handling of change over time, and the lack of stage-level diagnostics do not. This is why we treat them as sources of prompts and algorithms and own the pipeline..

These gaps set the design principles. First, start from the simplest baseline, embedding-similarity search over text chunks, and build every graph feature as an optional layer that references chunk IDs, so the baseline always works and every enhancement can be compared against it. Second, keep extracted knowledge as free text with minimal fixed structure (relationships can connect more than two entities), and allow database-specific schemas only where free text proves insufficient. Third, log every query and result at the tool layer, and let calling agents report how relevant the results were and how they used them, so evidence of failure accumulates during ordinary use. Fourth, evaluate against LLM-generated questions with known supporting passages, comparing retrievers and databases on identical questions, which lets measured failures set the order of improvements. Fifth, keep the viewing interface minimal, a read-only log of sessions and events, so that maintaining it does not compete with the project itself.
